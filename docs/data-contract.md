# Data contract: players, matches and storage

Status: step M1.2, base `82ebb23`. **Both humans accepted it on 2026-10-20** — Niklas (ladder
track) and Eric (fun track) — so it becomes binding when this PR merges. Changing it afterwards
needs both of them to agree. The questions that were still open when it was written are
answered in section 9; the ones that are still open are listed there too, each with the
default the text uses.

This document states requirements and record shapes. It does not choose a library or database engine. The JSON shown is the logical shape; M1.3 decides how it is stored, as long as every rule below holds.

Words: MUST and MUST NOT are binding. "Rejected" always means: the request fails with a clear message, and nothing is stored or changed.

## 1. Player

| Field | Type | Rules |
|---|---|---|
| `id` | string | Opaque and generated by the server (for example `p_` plus random characters). Never chosen by the client, never changed, never reused, even if a player were removed. Every match and rating refers to this ID, never to the name. |
| `name` | string | The display name. See validation below. May be changed later; matches are unaffected because they hold the ID. |
| `externalLogin` | object or null | Empty (`null`) in the demo. Reserved for the later 42 intra login (M5.1), for example `{ "provider": "42", "subject": "..." }`. Adding it to an existing player MUST NOT change `id`, so matches and ratings stay linked. |
| `createdAt` | string | UTC time in ISO 8601, for example `2026-10-20T14:03:00.000Z`. Set by the server. |

**Name validation.** Leading and trailing whitespace is removed and runs of inner whitespace become one space. After that the name MUST be 1 to 30 characters, MUST NOT be empty or whitespace only, and MUST NOT contain control characters. Letters from any language, digits, punctuation and emoji are allowed. Anything else is rejected.

**Duplicate names.** Two players MUST NOT share a display name, compared case-insensitively after the clean-up above (`Anna` and ` anna ` collide). Reason: with no login, the name is how people pick themselves and others on a phone; two identical names would make the ladder unreadable. Creating a player with a taken name is rejected. (Decided by Niklas, 2026-10-20, Q1. Renaming and picking "me" stay open in Q1.)

**Not stored on the player:** rating, wins, losses, queue position. These are derived from matches or belong to track-specific records (section 5).

Example:

```json
{ "id": "p_8f3k2", "name": "Anna", "externalLogin": null, "createdAt": "2026-10-20T14:03:00.000Z" }
```

## 2. Match

One record type for every mode. Ranked, casual and fun matches differ by `mode`, not by separate tables.

| Field | Type | Rules |
|---|---|---|
| `id` | string | Server-generated, opaque, never reused (for example `m_` plus random characters). |
| `mode` | string | `ranked`, `casual`, or a fun-mode value. Initial fun value: `merry-go-round`. New values are added by agreement of both humans (section 5) and need no change to stored records. Code that reads an unknown mode MUST show the match as-is and MUST NOT crash or change it. Only `ranked` ever counts for ratings. |
| `state` | string | See the state table below. |
| `participants` | array of player IDs | 2 or more IDs, no duplicates, every ID an existing player. Order is the order given at creation and has no ranking meaning. `ranked` and `casual` have exactly 2. `merry-go-round` has 3 or more. |
| `createdBy` | player ID | The player who created the match, or `null` when the server created it (for example the ranked queue pairing, M2.2). |
| `result` | object or null | `null` until a result is reported. Exception: a running multi-player round in state `accepted` holds a partial result (eliminations only, no `winner`). Shape below. |
| `reportedBy` | player ID or null | Who reported the current result. |
| `decidedBy` | player ID or null | Who made the latest accept, decline, cancel, confirm or dispute decision. |
| `details` | object | Optional mode-specific extras. Starts as `{}`. Only the owning track (section 5) adds keys, and unknown keys MUST be preserved when a record is rewritten. |
| `createdAt` | string | ISO 8601 UTC. |
| `updatedAt` | string | ISO 8601 UTC, changed on every transition and on every appended elimination. |
| `reportedAt`, `confirmedAt` | string or null | Set on the matching transition. `confirmedAt` is also what orders replay for Elo (section 5). |

### Result

For two-player matches (`ranked`, `casual`):

```json
{ "scores": { "p_8f3k2": 2, "p_1a9xq": 1 } }
```

`scores` has exactly one non-negative whole number per participant. The scores MUST NOT be equal: a match with no winner is rejected, because table tennis has no draw. The winner is the higher score and is not stored separately, so it cannot disagree with the scores. For ranked matches a score is the number of games won in a best-of match (for example 2-1), not points within one game (decided by Niklas, 2026-10-20, Q8). Points per game are out of scope.

For multi-player matches (`merry-go-round`):

```json
{ "eliminations": ["p_c", "p_b"], "winner": "p_a" }
```

`eliminations` lists participants in the order they went out, first out first. It contains no duplicates and only participants. `winner` is the one participant who was never eliminated and is present only when `eliminations` has exactly (participants minus 1) entries. Final placing is therefore: winner first, then the eliminations in reverse order. While a round is running, `result` holds the partial `eliminations` list without `winner`.

### States and transitions

| State | Meaning |
|---|---|
| `proposed` | Created, waiting for the other side. |
| `accepted` | Agreed to be played (or running, for multi-player modes). |
| `reported` | A final result has been entered and awaits confirmation (where required). |
| `confirmed` | Final. Counts for history, and for ratings if `ranked`. |
| `disputed` | The confirmer (the participant who did not report) says the reported result is wrong. Never counts. |
| `declined` | The invitee refused. Final. Records no result, and **never counts as a played match**: it is not shown in the played-match list (M3.1 decides the UI; the record itself is kept as history). |
| `cancelled` | Withdrawn before a result was reported. Final. |

Allowed transitions, and nothing else:

| From | To | Applies to | Meaning |
|---|---|---|---|
| (new) | `proposed` | `ranked` | Created by the server only (queue pairing, or tournament in M2.4); `createdBy` is `null`. |
| (new) | `proposed` | `casual` | Invite created by a player. |
| (new) | `accepted` | `merry-go-round` | Starter lists everyone at the table; no invitation step. |
| `proposed` | `accepted` | `casual` | Invitee accepts. |
| `proposed` | `reported` | `ranked` | A ranked match needs no acceptance (the server created it from a queue pairing or a tournament, so both players already agreed). |
| `proposed` | `declined` | `casual` | Invitee declines. |
| `proposed`, `accepted` | `cancelled` | all | Withdrawn before a final result is reported; who may do it is in section 3. A multi-player round with partial eliminations can still be cancelled by the starter until the winner is determined. |
| `accepted` | `reported` | `casual`, `merry-go-round` | Final result entered. For merry-go-round, eliminations are first appended while the state stays `accepted`; the match moves to `reported` when the last remaining player is the winner. |
| `reported` | `confirmed` | `ranked` | The participant who did not report agrees. |
| `reported` | `confirmed` | `casual`, `merry-go-round` | Happens at the same moment as reporting. No second person confirms (see Q2), but both `reportedAt` and `confirmedAt` are set. |
| `reported` | `disputed` | `ranked` | The participant who did not report disagrees. |
| `disputed` | `reported` | `ranked` | A participant reports a corrected result, which needs confirming again. |
| `disputed` | `cancelled` | `ranked` | Players give up. |

`declined`, `cancelled` and `confirmed` are final: no further transition, no edits to the result. Any request that is not in the table is rejected. This includes confirming a match that is already `confirmed`.

## 3. Who may do what

There is no login in the demo. The app asks "who are you?" and the client sends the chosen player ID as the **acting player**. This is an **honour system**: the server cannot tell whether the person at the phone is that player, so these rules guard against mistakes and casual cheating, not against a determined impostor. Anti-cheat beyond result confirmation is out of scope (IDEA.md). After M5.1 the acting player comes from the login instead; the rules below do not change.

Every action is checked against the acting player. An acting player who does not exist, or is not allowed, is rejected.

| Action | `ranked` | `casual` | `merry-go-round` |
|---|---|---|---|
| Create | Only the server (queue pairing, or tournament in M2.4); `createdBy` is `null`. A player cannot create a ranked match, not even against a named opponent; targeted games use casual invites (decided by Niklas, 2026-10-20, Q11). | The inviter, who MUST be one of the 2 participants and not the invitee. | The starter, who MUST be one of the participants. |
| Accept | not needed | Only the invitee (the participant who is not `createdBy`). | not needed |
| Decline | not applicable | Only the invitee. | not applicable |
| Cancel | Either participant, before a result is reported (or after a dispute). Ranked matches have no creator, so this applies to both. | The inviter (the invitee declines instead). | The starter. |
| Report result | Either participant. | Either participant. | Any participant may record the next elimination. The same player cannot be recorded twice. |
| Confirm | Only the participant who did **not** report (decided by Niklas, 2026-10-20, Q4). If the loser reports their own loss, the winner confirms. The reporter can never confirm their own report. | Automatic with the report. | Automatic with the final report. |
| Dispute | Only the participant who did not report, same person as the confirmer. | not applicable | not applicable |
| Report a correction after a dispute | Either participant. | not applicable | not applicable |

Notes:

- The rule "the non-reporter confirms" means nobody confirms their own report. Whoever reports, the other participant must agree before ratings move.
- After a dispute, whoever reports the correction is the reporter; the other participant confirms or disputes it.
- The server MUST check the acting player against stored data, not against whatever the browser claims about itself.
- A player who never confirms leaves the match in `reported` and the ratings unchanged. Whether stale matches expire is not decided here (Q3).

## 4. Ratings are derived

- Starting rating 1000, K-factor 32 (decided 2026-10-20).
- A rating is **never typed in or stored as a source of truth**. It is the result of replaying all matches with `mode = ranked` and `state = confirmed`, ordered by `confirmedAt` and then by match `id`, starting every player at 1000. The same match history MUST always give the same ladder. A cached rating is allowed only if it can be rebuilt by that replay and is rebuilt when they differ.
- No other record changes a rating. In particular a `casual` or fun match, a `proposed`, `reported`, `disputed`, `declined` or `cancelled` match can never change a rating. A player with no confirmed ranked match has 1000.
- The exact Elo formula and rounding belong to M2.1. Two fixed checks from the ladder brief: two players at 1000 give 1016 for the winner and 984 for the loser, and the winner always gains exactly what the loser loses.

## 5. Which track owns what

Owner means: the only track that may add or change the meaning of the item. The other track reads it. A change to any "shared" item needs both humans.

| Item | Owner |
|---|---|
| Player record (section 1), including name rules and `externalLogin` | Shared (M1.3 builds it, Eric owns that step) |
| Match envelope: `id`, `mode`, `state`, `participants`, `createdBy`, timestamps, the state table | Shared |
| `mode = ranked`, its result, report/confirm/dispute rules | Niklas (ladder) |
| Ratings, ladder, Elo replay | Niklas. Derived, never entered. |
| Ranked queue (who is waiting) | Niklas. A separate record, not a match, until a pair is formed. |
| Tournaments and brackets | Niklas. A tournament is a separate record that refers to match IDs; a bracket match is an ordinary `ranked` match: it counts as ranked and changes Elo once confirmed (decided by Niklas, 2026-10-20, Q6). Its record shape is defined in M2.4. |
| `mode = casual`, invites, accept/decline | Eric (fun) |
| `mode = merry-go-round` and later fun modes, their `eliminations` result and `details` keys | Eric (fun) |

Rules that follow:

- A new fun-mode value is a proposal by Eric and is added to this document in the same PR that first uses it. It MUST NOT use a transition that is not in section 2 without both humans agreeing.
- Fun modes and `casual` never write ratings and never appear in the Elo replay (section 4). The Elo code MUST filter on `mode = ranked` by exact match, not by "anything except casual".
- Both tracks write through the same player and match code from M1.3, so the rules in sections 1 to 3 are enforced in one place.

## 6. Storage

Requirements:

1. All durable data (players, matches, and track records such as the queue) lives **on the server, outside the release directories**. Default location: `~/.local/share/vibecode-workshop/data/`. A path from an environment variable (proposed name `DATA_DIR`) overrides the default, so tests can use a temporary folder. If the location is missing the app creates it; if it cannot be created or written the app fails visibly rather than running with data lost.
2. Data survives page reloads, other visitors, an app restart and a redeploy (a new release directory). A deploy MUST NOT delete, reset or migrate away existing data without a written migration step.
3. **No lost records under concurrent writes.** If two visitors create a player or report a match at the same moment, both records exist afterwards. If two requests change the same match at the same moment (for example two confirmations), exactly one wins and the other is rejected as an invalid transition; the stored match is never half-written or a mix of both.
4. A crash or restart in the middle of a write leaves either the previous or the new state, never a corrupt file.
5. Stored records are never edited by hand in the shared demo; fixes happen through the app or a written migration.
6. Stored data may contain player names, so it is not served as a web asset and not committed to Git.
7. Records carry enough to be read by a later version: unknown fields are preserved, and a stored `schemaVersion` (a number, starting at 1) lets M1.3 and later steps migrate. It sits on every stored record (each player, each match), not once per store.

Implementation choice (file, SQLite or other) is for M1.3. It must be explained there and has to satisfy requirement 3 in particular.

## 7. Failure and boundary cases

Every case below is rejected: a clear message, no record created or changed.

| Case | Expected |
|---|---|
| Match with a participant ID that is not an existing player | Rejected. Nothing stored. |
| The same player listed twice in one match (including inviting yourself) | Rejected. |
| Fewer than 2 participants, or a `ranked` / `casual` match with other than 2 | Rejected. |
| Fun mode (`merry-go-round`) with fewer than 3 participants | Rejected. |
| Result with equal scores (no winner), or a missing score, or a negative or non-whole score | Rejected. The match keeps its previous state. |
| Result that names a player who is not a participant | Rejected. |
| Elimination recorded twice for the same player, or for the winner after the round ended | Rejected. |
| Confirm on a match that is already `confirmed` (second confirmation) | Rejected. The first confirmation and `confirmedAt` stay unchanged. |
| Confirm or dispute by the reporter or a non-participant; accept or decline by someone other than the invitee | Rejected. |
| Any transition not in the section 2 table (for example report on a `declined` match, accept after `cancelled`) | Rejected. |
| A client request to create a `ranked` match | Rejected. Only the server creates ranked matches. |
| Unknown `mode` value on creation | Rejected. (Unknown modes already stored are shown but never changed.) |
| Player name that is empty, too long, or already taken | Rejected. |
| Acting player does not exist | Rejected. |

## 8. Worked examples

IDs are shortened for reading. `schemaVersion` is omitted from the match records for brevity; they would carry it per section 6.

### 8.1 Ranked 1v1, report to confirmation

Players Anna (`p_anna`) and Ben (`p_ben`) both have 1000. The queue pairs them; the server creates the match.

After creation (state `proposed`):

```json
{ "id": "m_001", "mode": "ranked", "state": "proposed",
  "participants": ["p_anna", "p_ben"], "createdBy": null,
  "result": null, "reportedBy": null, "decidedBy": null, "details": {},
  "createdAt": "2026-10-20T14:10:00.000Z", "updatedAt": "2026-10-20T14:10:00.000Z",
  "reportedAt": null, "confirmedAt": null }
```

Anna wins 2-1 and reports (acting player `p_anna`). State becomes `reported`:

```json
{ "id": "m_001", "mode": "ranked", "state": "reported",
  "participants": ["p_anna", "p_ben"], "createdBy": null,
  "result": { "scores": { "p_anna": 2, "p_ben": 1 } },
  "reportedBy": "p_anna", "decidedBy": null, "details": {},
  "createdAt": "2026-10-20T14:10:00.000Z", "updatedAt": "2026-10-20T14:25:00.000Z",
  "reportedAt": "2026-10-20T14:25:00.000Z", "confirmedAt": null }
```

Ratings are still 1000 / 1000. Ben, who did not report, confirms. If Anna tried to confirm her own report, it would be rejected. The same holds if Ben, the loser, had reported his own loss: then Anna (the winner, not the reporter) would confirm and Ben could not.

```json
{ "id": "m_001", "mode": "ranked", "state": "confirmed",
  "participants": ["p_anna", "p_ben"], "createdBy": null,
  "result": { "scores": { "p_anna": 2, "p_ben": 1 } },
  "reportedBy": "p_anna", "decidedBy": "p_ben", "details": {},
  "createdAt": "2026-10-20T14:10:00.000Z", "updatedAt": "2026-10-20T14:27:00.000Z",
  "reportedAt": "2026-10-20T14:25:00.000Z", "confirmedAt": "2026-10-20T14:27:00.000Z" }
```

Replay now gives Anna 1016 and Ben 984. A second confirmation is rejected and changes nothing.

### 8.2 Casual invite that is declined

Anna invites Ben to a casual game. Created by `p_anna`, state `proposed`. Ben declines (acting player `p_ben`):

```json
{ "id": "m_002", "mode": "casual", "state": "declined",
  "participants": ["p_anna", "p_ben"], "createdBy": "p_anna",
  "result": null, "reportedBy": null, "decidedBy": "p_ben", "details": {},
  "createdAt": "2026-10-20T15:00:00.000Z", "updatedAt": "2026-10-20T15:02:00.000Z",
  "reportedAt": null, "confirmedAt": null }
```

The record stays as history, has no result, and is final. Ratings are unchanged. A declined
invite **never counts as a played match**: M3.1 hides declined matches from the played-match
list, so it leaves no trace in the match history a player reads (decided by Eric, 2026-10-20,
Q10). `.ai/team/eric.md` was reworded to match.

### 8.3 Merry-go-round with 3 players

Anna, Ben and Cem (`p_cem`) start a round; Anna starts it. State `accepted`, `result` `{ "eliminations": [] }`. Cem is eliminated first, then Ben (each elimination updates `updatedAt`). After the second elimination only Anna remains, so the match becomes `reported` and, per section 2, `confirmed` at once:

```json
{ "id": "m_003", "mode": "merry-go-round", "state": "confirmed",
  "participants": ["p_anna", "p_ben", "p_cem"], "createdBy": "p_anna",
  "result": { "eliminations": ["p_cem", "p_ben"], "winner": "p_anna" },
  "reportedBy": "p_anna", "decidedBy": null, "details": {},
  "createdAt": "2026-10-20T16:00:00.000Z", "updatedAt": "2026-10-20T16:12:00.000Z",
  "reportedAt": "2026-10-20T16:12:00.000Z", "confirmedAt": "2026-10-20T16:12:00.000Z" }
```

Placings: 1st Anna, 2nd Ben, 3rd Cem. No rating changes. Recording Cem as eliminated again is rejected.

## 9. Decisions and open questions

### Decided (Niklas, ladder track, 2026-10-20)

- **Q1 (part).** Display names are unique, compared case-insensitively after trimming.
- **Q4.** A reported ranked result is always confirmed by the participant who did not report. If the loser reports their own loss, the winner confirms.
- **Q11.** Ranked matches are created only by queue pairing (or by a tournament, M2.4). There is no direct ranked challenge; targeted games go through casual invites.
- **Q6.** Tournament matches are `ranked` and change Elo once confirmed.
- **Q8.** A ranked score is games won in a best-of match (for example 2-1), not points within one game.

### Decided (Eric, fun track, 2026-10-20)

- **Q1 (rest). Renaming and "me".** The default is kept: a player **may rename themselves** (the name rules and the uniqueness rule still apply), and **anyone may pick any existing player** as "me" — the honour system of section 3. This is what makes picking yourself on a phone work.
- **Q2. Casual and fun confirmation.** **No confirmation.** The report is final for `casual` and for fun modes; the opponent does not have to agree. Casual and fun matches never change ratings, so a second confirmation would only add friction next to the table. Only `ranked` needs the non-reporter to confirm.
- **Q7. Meaning of "invite".** "Invite" means inviting another player **inside our own app**, not integrating with 42 intra. The 42 intra login stays the later step M5.1, and this contract is already shaped for it (`externalLogin`).
- **Q10. Declined invites.** The `declined` record is **kept** (the default in this contract): it has no result, it never counts as a played match, and M3.1 hides declined matches from the played-match list. `.ai/team/eric.md` was reworded from "a declined invite records no match" to "a declined invite has no result and does not count as a played match".

### Open (NOT decided; the text above uses the stated default so work can proceed)

- **Q3. Stale matches.** A `reported` ranked result never confirmed, or a `proposed` match nobody answers, stays open forever by default. Should it time out, or may either player cancel it? Niklas decides.
- **Q5. Cancel and dispute limits for ranked.** Default: either participant may cancel before a result is reported or after a dispute, and dispute/correct rounds are unlimited. Niklas decides.
- **Q9. Data location variable.** Is `DATA_DIR` the agreed name, and is `~/.local/share/vibecode-workshop/data/` writable by the app user on the guest (M1.1 evidence)? M1.3 verifies.
